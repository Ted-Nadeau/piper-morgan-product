## Spec Review: #858 Conversation Lifecycle

### Overall Assessment

**Verdict**: Strong spec. Ready for implementation with minor clarifications.

The Lead Dev has done excellent work synthesizing the CXO/PPM input into a coherent design. The design principles are particularly well-articulated, and the forward-compatibility considerations (multi-entity, branching) show architectural maturity.

---

### Strengths

**1. Design Principles (Section 1)**

P2 ("Entity Surface, Not Conversation Archive") is the key insight. This positions the right sidebar correctly for future entity types. The anti-flattening checklist at P6 operationalizes the principles — good.

**2. State Machine (Section 2)**

Clean, well-defined transitions. The distinction between internal states (ACTIVE/ARCHIVED/COMPOSTED/DELETED) and user-visible states (just there / older / remembered / gone) follows the Colleague Test appropriately.

**3. Multi-Entity Compatibility (P3)**

The language choices (`created_by` vs `user_id`, topic-centric naming) properly anticipate PDR-101. This avoids rework when multi-participant conversations arrive.

**4. Migration Path (Section 2.5, Appendix B)**

Thoughtful backward compatibility: `is_active` becomes computed property, existing API consumers get default behavior. No breaking changes until #715 implements new UI.

**5. Test Coverage (Section 8)**

Comprehensive. T14 (full lifecycle E2E) is the critical path test. The naming tests (T15-T16) enforce P4 (State Is Visual, Not Nominal).

---

### Questions / Clarifications Needed

**Q1: COMPOSTED Operational Definition**

Section 2.3 says ARCHIVED → COMPOSTED involves "content distilled into learning." What does this mean operationally?

- Is there actual code that extracts learnings from archived conversations?
- Does COMPOSTED mean "content deleted, only learnings remain" or "content preserved but not surfaced"?
- If the former, is there a data retention policy concern?

**Recommendation**: Add a sentence clarifying whether COMPOSTED retains original content (just hidden) or actually deletes it after distillation.

**Q2: Timezone Handling for Day Boundary**

Section 4 says the soft close trigger is "calendar day boundary passes with no new user messages." Whose calendar day?

- Server UTC?
- User's local timezone (if known)?
- Session timezone?

**Recommendation**: Specify timezone policy. Suggest: user's timezone if available (from browser or profile), otherwise server UTC.

**Q3: 30-Day ARCHIVED → COMPOSTED Default**

Section 2.3 mentions "configurable period (default: 30 days)" for composting. Where is this configured?

- User preference?
- System config?
- Per-workspace setting?

**Recommendation**: Clarify configuration location. For alpha, system config is fine. For beta, consider user preference.

**Q4: COMPOSTED Visibility in Right Sidebar**

Section 2.2 says COMPOSTED is "Not visible" and user sees "Piper remembers things" implicitly. But Section 5.1 (Sidebar Identity) doesn't mention COMPOSTED at all in the right sidebar behavior.

Should the right sidebar have a "Show composted" toggle? Or is COMPOSTED truly invisible (only accessible via Piper's memory)?

**Recommendation**: Explicitly state whether COMPOSTED conversations are ever directly accessible, or only through Piper's synthesized memory.

---

### Minor Suggestions

**S1: State Transition Audit Trail**

Consider adding `state_changed_at` or a transition log. Useful for debugging lifecycle issues and for future analytics ("how long do conversations stay active on average?").

**S2: Bulk Operations**

The spec focuses on single-conversation actions. Should there be bulk archive/delete? "Archive all conversations older than X" is a natural user need.

**S3: Composting Transparency**

P1 says users see "Piper remembers things" for COMPOSTED. But how does the user know what Piper remembers? Consider a future "What do you remember about X?" query that surfaces composted learnings.
