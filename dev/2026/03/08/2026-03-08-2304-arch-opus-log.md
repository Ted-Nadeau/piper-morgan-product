## Async Workflow Analysis

### The Problem

The intent processing pipeline creates a `Workflow` database row for every intent. This was designed for async orchestration (long-running analysis, multi-step planning). But 26 of 27 handlers are fully synchronous — they return immediately.

Result:
- Wasted DB writes
- Unused workflow rows accumulate in "pending" state forever
- Frontend was polling for 60 seconds on every response (now fixed)

### Option Assessment

| Option | Effort | Cleanliness | When to Choose |
|--------|--------|-------------|----------------|
| **A: Lazy workflow creation** | 2-3 hours | Clean | If async orchestration is coming |
| **B: Keep current + flag** | Zero | Acceptable | If workflows stay unused |
| **C: Replace with telemetry** | Large | Right-sized | If we decide workflow is wrong abstraction |

### My Recommendation: Option A

**Rationale**:

1. **Async orchestration IS coming**. The M1/M2 roadmap includes multi-step planning, long-running analysis, and potentially background jobs. These are real async use cases.

2. **Lazy creation is the right pattern**. Pass a `create_workflow_if_needed()` factory to handlers. Only handlers that start async work call it. This is explicit, intention-revealing, and prevents accidental workflow creation.

3. **The refactor is bounded**. 2-3 hours is modest. The main risk (telemetry/logging depending on workflow existence) can be mitigated by checking call sites during the refactor.

4. **Option B accumulates debt**. "Keep it and flag it" works today but leaves orphaned rows and semantic confusion. We'd be kicking the can.

5. **Option C is premature**. We don't know yet whether workflow is the wrong abstraction. Let's see how async orchestration evolves before replacing it.

### Implementation Guidance

```python
# Before (current)
workflow = workflow_service.create(intent_id=...)
result = handler(workflow_id=workflow.id, ...)

# After (Option A)
def create_workflow_if_needed() -> str:
    return workflow_service.create(intent_id=...).id

result = handler(create_workflow=create_workflow_if_needed, ...)
# Handler calls create_workflow() only if starting async work
```

**Migration path**:
1. Add `create_workflow` parameter to handler signature
2. Update `_handle_generic_query` to call it
3. Remove pre-creation from `process_intent()`
4. Verify no telemetry/logging breaks
5. Clean up orphaned workflow rows (one-time migration)

## PDR-003 Architectural Review

**Document**: PDR-003 Entity Concept Model — Product, Project, Repository
**Authors**: PPM, CXO
**Status**: DRAFT (CXO approved, awaiting Architect)
**Date of review**: March 8, 2026

### Verdict: APPROVED

PDR-003 is architecturally sound and ready for implementation.

### Strengths

**1. Clear concept separation**

The definitions are crisp and user-grounded:
- **Product**: "The thing you're building and shipping"
- **Project**: "A bounded effort with intent"
- **Repository**: "Where code lives"

The "Typical PM questions" framing is excellent — it grounds each concept in how users actually think.

**2. Correct relationship cardinalities**

| Relationship | Cardinality | Rationale |
|--------------|-------------|-----------|
| Product ↔ Project | Many-to-many | Platform projects serve multiple products |
| Project ↔ Repository | Many-to-many | Monorepos, shared libraries |
| Product ↔ Repository | Derived | Correct — avoids redundant direct relationship |

The decision to make Product ↔ Repository **derived** (`Product → Projects → Repositories`) is architecturally correct. It avoids sync issues and respects the actual dependency chain.

**3. Progressive disclosure is the right strategy**

The 4-phase approach:
1. MVP: Repository first-class (done in M0!)
2. Settings-based Product management
3. Conversational Product emergence
4. Onboarding integration (if data warrants)

This respects the Cathedral principle: build infrastructure before features. And it honors the Emergence Principle: "Products emerge from projects, not the other way around."

**4. Removes architectural debt**

The `Project extends Product` inheritance was wrong. Inheritance implies "is-a"; a Project is not a specialized Product. They're distinct concepts with a relationship. The many-to-many join table is correct.

**5. Self-test with Piper Morgan**

Applying the model to our own usage validates it handles real-world complexity:
- 1 Product, 5 Projects, 3 Repos
- Repo "platform" linked to 3 projects
- Clear cardinality demonstration

### Minor Clarifications (for documentation only, not blocking)

**1. Owner semantics**

PDR-003 says "The user who connected [the repo] owns it." Clarify: this is `owner_id` on Repository, distinct from GitHub repo owner. Consider naming it `connected_by_user_id` to avoid confusion with GitHub semantics.

**2. Default behavior**

When a user connects a repo, should it auto-link to their current project? The UX flow implies yes, but the model doesn't specify. Recommend: default to linking to current project, with option to change.

**3. Archive cascade**

If a Project is archived, should its repo links be preserved? (I assume yes — archiving is soft-delete, not unlinking.) Worth stating explicitly.

### Implementation Readiness

Phase 1 (Repository as first-class) was **already implemented** in M0:

- #859-863: CRUD, setup wizard, settings UI, conversational handler

Phase 2 (Product ↔ Project relationship) is ready for M1/M2:
- Create `product_projects` join table
- Add Product management to settings
- Remove inheritance
