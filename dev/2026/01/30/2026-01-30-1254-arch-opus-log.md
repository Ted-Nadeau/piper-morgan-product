### Memo 2: Multi-Tenancy Isolation Layer (Jan 30) - HIGH PRIORITY

**Context**: #734 calendar tokens leaking between users revealed systemic multi-tenancy isolation failures across 38+ locations.

**PM Decisions Already Made**:
- LLM keys: Per-user (may change for enterprise later)
- workspace_id: Activate now
- Migration: Not a concern (few alpha users)
- Approach: Option C - Full domain-driven refactor

**Lead Dev is asking 6 questions. My analysis:**

#### Q1: OAuth Credential Separation Pattern

**Options presented**:
- A) Different storage mechanisms
- B) Different key prefixes
- C) Different services entirely

**My recommendation**: **Option C - Different services**

Rationale:
- App credentials (client_id, client_secret) = **system configuration** → `IntegrationConfigService`
- User tokens (access_token, refresh_token) = **user data** → `UserTokenService` (or extend `UserAPIKeyService`)

This aligns with domain-driven design: credentials that belong to different bounded contexts should have different services. App creds are infrastructure; user tokens are user data.

**Implementation note**: App credentials can stay in environment variables or a system config table. User tokens must be in the user-scoped data layer with `owner_id` enforcement.

---

#### Q2: RequestContext Activation Strategy

**Options presented**:
- A) Big bang: Required everywhere at once
- B) Gradual: Deprecation warnings then enforce
- C) Boundary enforcement: Required at route level, optional deeper

**My recommendation**: **Option C - Boundary enforcement**

Rationale:
- Routes are the trust boundary - this is where user identity is established
- Services can trust they receive valid context from routes
- Background tasks need explicit handling (separate pattern)
- Avoids "None-checking everywhere" anti-pattern

**Implementation note**: Create a middleware or dependency that ensures RequestContext exists for all authenticated routes. Services that need user context should receive it as a required parameter. Services that are user-agnostic don't need it.

---

#### Q3: Integration Adapter User Context

**Sub-questions**:
- Should config services be instantiated per-request?
- How do OAuth callbacks identify the initiating user?
- How do background tasks maintain user context?

**My recommendations**:

**Config services**: No, keep as singletons but **pass user context to methods**:
```python
# Current (broken)
config_service.get_calendar_token()

# Correct
config_service.get_user_calendar_token(user_id)
```

**OAuth callbacks**: **Embed user_id in OAuth state parameter**. This is the standard pattern:
```python
state = {"user_id": user_id, "return_url": "/settings", "nonce": random_nonce()}
encoded_state = base64_encode(json.dumps(state))
# Pass encoded_state to OAuth provider
# On callback, decode state to recover user_id
```

**Background tasks (webhooks)**: Two patterns depending on webhook type:
1. **User-initiated webhooks** (Slack message from user): Extract user from webhook payload → lookup internal user_id
2. **System webhooks** (GitHub push): May need to store "who connected this integration" and use that as the acting user

---

#### Q4: Singleton Manager Refactor

**Options presented**:
- A) Key by user_id instead of session_id
- B) Database-backed state
- C) Per-user instances

**My recommendation**: **Option A (key by user_id) with consideration for Option B later**

Rationale:
- `session_id` is ephemeral (browser tab) - wrong granularity
- `user_id` is the identity boundary - correct granularity
- Database backing is good for durability but adds complexity
- For MVP, in-memory keyed by user_id is sufficient

**Implementation note**: Change the dictionary key from `session_id` to `user_id`. The cleanup timeout behavior can stay the same. Database backing can be added later if restart persistence becomes important.

---

#### Q5: Repository Isolation Pattern

**Options presented**:
- A) Make owner_id required (breaking change)
- B) Add workspace_id alongside owner_id
- C) Per-user repository instances

**My recommendation**: **Option A with Option B as follow-on**

Rationale:
- Making `owner_id` required **catches missing context at compile/test time** rather than runtime
- This is the "fail fast" principle - better to break loudly than leak silently
- `workspace_id` should be added but as a second dimension (users within workspaces)

**Implementation note**:
1. First, make `owner_id` required → fix all call sites
2. Then, add `workspace_id` as optional with default (for future multi-tenant)
3. Consider a `TenantContext` dataclass that bundles both

---

#### Q6: Sequencing Recommendation

**Lead Dev's proposed order**:
1. RequestContext enforcement (foundation)
2. OAuth state redesign (user identification)
3. Credential storage (UserAPIKeyService for all)
4. Config service refactor (per-user context)
5. Repository isolation (workspace activation)

**My assessment**: Good sequence, but I'd adjust slightly:

**Recommended sequence**:

1. **RequestContext enforcement** ✓ (foundation - all other work depends on this)
2. **Repository isolation (owner_id required)** ← Move up (this catches more bugs early)
3. **OAuth state redesign** (now repos won't accept None owner_id)
4. **Credential storage separation** (app vs user)
5. **Config service method signatures** (pass user context to methods)
6. **Singleton manager refactor** (can run parallel with 4-5)
7. **workspace_id activation** (last - needs all above in place)

**Rationale for reorder**: Making owner_id required early creates a "forcing function" - any code path that doesn't have user context will fail immediately, revealing all the places that need fixing.

## Additional Architectural Considerations

### 1. Audit Trail
With multi-tenancy, consider adding `acted_as_user_id` to sensitive operations for audit purposes.

### 2. Testing Strategy
Need integration tests that verify cross-user isolation:
- User A creates data → User B cannot see it
- User A's tokens are not accessible from User B's context

### 3. Error Messages
Ensure "not found" vs "not authorized" distinction is handled carefully to prevent information leakage.

### 4. Background Job Context
Consider a `JobContext` that captures the user context at job creation time and restores it at execution time.
