## Analysis: Offer System Design

### The Core Problem

The Lead Dev has correctly identified a structural gap. The issue isn't the specific bug (#846) — it's that we have two implicit categories of offers with no explicit distinction in the code.

### Evaluating the Options

**Option A: Make all offers structured**

This is the "everything is a nail" approach. It would work, but it forces conversational language into system contracts. "Would you like to explore more of our history?" doesn't have a meaningful `workflow_type`. We'd be inventing phantom workflows just to satisfy the type system.

Verdict: Overengineered. Treats the symptom, not the cause.

**Option B: Text-based offer detection**

This is fragile architecture. We'd be coupling system behavior to prose patterns. What happens when someone writes "Want me to help?" instead of "Would you like me to help?" Or when the LLM generates a variation? We'd be playing regex whack-a-mole forever.

Verdict: Technical debt factory. Avoid.

**Option C: Separate real offers from rhetorical questions**

This is the right instinct, but the Lead Dev is correct that "the boundary is fuzzy." The question is: can we make it unfuzzy?

### My Position: Option C with a Bright-Line Rule

The distinction isn't "real vs rhetorical" — that's subjective. The distinction is:

**Actionable Offer**: The "yes" response triggers a *specific, predefined workflow*.
- "Would you like me to help you set up your priority list?" → YES triggers `configure_priorities` workflow
- "Would you like to add a project?" → YES triggers `add_project` workflow

**Contextual Continuation**: The "yes" response continues the *current conversational thread* with more of the same.
- "Would you like me to explain more about how Piper uses project context?" → YES means "continue explaining"
- "Would you like to explore more of our history?" → YES means "show me more history"

The bright-line rule:

> **If "yes" should invoke a named workflow, use `action_required`. If "yes" means "continue/elaborate," let the LLM handle it contextually.**

### Why This Works

1. **Clear decision point**: When writing a handler, ask: "Does 'yes' start a workflow, or does it mean 'tell me more'?" This is answerable.

2. **No phantom workflows**: We don't invent `explain_project_context` as a workflow. That's just conversation.

3. **LLM handles the soft stuff**: The LLM is actually good at "user said yes after I offered to elaborate — I should elaborate." That's what LLMs do. We just need to ensure the conversation context is available.

4. **Structured system stays clean**: `action_required` means what it says — an action is required from the system.

### The Gap to Fill

The Lead Dev notes that the LLM handling of contextual continuations is "a coin flip." That's a separate concern:

**Issue**: LLM classifier doesn't reliably recognize "yes" as continuation of previous offer.

**Fix**: Enhance `ConversationContext` to track "last offer type" (ACTIONABLE vs CONTEXTUAL). When the LLM sees a bare "yes/no" after a CONTEXTUAL offer, it should interpret it as continuation, not classify from scratch.

This is a small enhancement to the lens/context system we just built in M0.

### Recommendation

1. **Adopt Option C with the bright-line rule** (actionable = workflow, contextual = LLM)

2. **Document the rule** in the implementation guide or as a pattern

3. **Create one issue** for improving contextual continuation handling — enhance ConversationContext to track offer type, improve LLM's yes/no-after-offer behavior

4. **Don't retrofit the 11 sites** — most of them are contextual continuations that should stay conversational. Review each to confirm, but I expect few (if any) need `action_required`.

5. **ADR not needed** — this is guidance/pattern level, not architectural decision. A section in the implementation guide or a new pattern (Pattern-062: Offer Classification) is sufficient.
