## 12:55 PM - Domain Model Memo Review

Read Lead Dev memo on Product, Project, and Repository relationships.

### Key Gaps Identified

1. **Repository**: Currently stored as config inside ProjectIntegration — can't exist independently or be shared
2. **Product ↔ Project**: Both entities exist but have zero relationship in the model

### CXO Analysis

Core UX question: What mental model do users bring?
- Solo PM: One product = one project = one repo (treats them as same thing)
- Startup PM: One product, multiple projects, multiple repos
- Enterprise PM: Multiple products, shared projects, shared repos

**Design goal**: Model that works for all three without forcing solo PM to understand enterprise complexity.

## 1:02 PM - CXO Response Memo Created

Created `memo-cxo-domain-model-response-2026-02-26.md` for PPM review.

### CXO Recommendations

| Question | Recommendation |
|----------|----------------|
| Repository entity | **Now** — first-class, many-to-many with projects |
| Product ↔ Project | **Late** — settings first, then conversational suggestion |
| Products in onboarding | **No** — let products emerge from use |

### Key Principle: Progressive Disclosure

Build the right domain model now (full many-to-many). Surface it progressively in UX:
- Start simple (projects, optionally repos)
- Introduce products when users have enough projects to need organization
- Let Piper suggest structure rather than requiring upfront definition

### The Emergence Principle

"Products emerge from projects, not the other way around."

This aligns with colleague framing: a colleague doesn't ask you to define your org chart before helping. They learn it over time and offer to help organize when they see the need.
