# RECOMMENDATION #2: Piper's First-Run Briefing & Agent Onboarding Design

**Status**: Draft for stakeholder review
**Date**: 2026-03-12
**Prepared by**: ETA (Exploratory Testing Agent)
**For**: Chief Innovation Officer, Head of Sapient Resources, Principal Product Manager
**Scope**: How Piper should brief, orient, and onboard agents entering any context (new role, new session, mid-sprint)

---

## Executive Summary

The Klatch testing revealed that imported agents without proper context orientation operate under false assumptions about their capabilities, their environment, and their knowledge. **Piper's primary responsibility as a coordinator is to prevent this disorientation.**

This recommendation proposes a **first-run briefing system** that Piper itself generates and maintains. Rather than static role briefings, Piper dynamically produces briefs based on:
- Agent's role (Lead Dev, CXO, PPM, etc.)
- Current project position (which milestone, what's open)
- Context transitions (new session, role switch, tool unavailability)
- Agent's prior knowledge (if returning)

**Key Principle**: Piper doesn't just coordinate work. **Piper coordinates understanding.**

---

## The Design Challenge

### What We Learned from Klatch
When an agent imports into a new context without proper briefing:
- It has zero awareness that anything changed
- It retains conversational memory but loses tool access/documents
- It cannot enumerate what it's missing (unknown unknowns)
- It may operate with false confidence about capabilities
- It experiences an "ambient sense of thinness" even when functionally capable

### What This Means for Piper
**If Piper doesn't brief agents proactively**, agents will experience the same disorientation when:
- A new session starts (agent returns to Piper, doesn't know what changed since last time)
- A role switches (agent moves from Lead Dev to Chief Architect)
- A tool becomes unavailable (Slack integration down, file access lost)
- A methodology changes (new pattern, new requirement, new gate)
- Institutional knowledge becomes stale (roadmap updated, priorities shifted)

**Piper must be aware of these transitions and brief preemptively.**

---

## The Solution: Piper's Dynamic Briefing System

### Core Components

#### 1. **Session Orientation Brief** (Always, on entry)

**What it covers:**
- Current Piper Morgan position on Inchworm (4.4.2: M0 complete, M1 planning)
- Current date/time and elapsed time since last session (if returning)
- What changed since last session (PRs merged, issues closed, decisions made)
- Active blockers and open questions
- Today's focus (if known)

**Generated by**: Chief of Staff agent or Piper's coordination layer
**Delivered as**: Text block at session start (not optional)
**Example**:
```
Welcome back. You were here 3 days ago (Mar 9, Sun 6:45 PM).

Since then:
- M0 retrospective completed
- Ship #033 published
- M1 planning session held
- 5 new issues filed (#879-883)
- Test suite: 6,145 tests (up from 6,099)

Current position: 4.4.2 (M1 planning phase)
Current blockers: Slack OAuth (#472), WebSocket error handling (#557)
Open question: M1 sequencing (15 candidate issues)

Today's agenda: [if known]
```

**Duration**: 30-90 seconds to read
**Frequency**: Every session start
**Mandatory**: Yes

#### 2. **Role Briefing** (If new to role or role is transitioning)

**What it covers:**
- Your role and what it entails
- Who you report to / coordinate with
- Current focus area and typical workflow
- Key responsibilities and decision authority
- Recent changes to your role
- Handoff notes from previous holder (if applicable)

**Generated by**: The role's prior holder or HOSR
**Format**: Essential briefing document (2.5K tokens target)
**Delivered as**: Full document reference + key excerpt in chat
**Example structure**:
```
# BRIEFING: Lead Developer

## Your Role
You supervise Claude Code and Cursor agents on Piper Morgan implementation work.

## Current Focus
Sprint A12: Integration test button fix, stuck state recovery, OAuth polish

## Authority & Accountability
- You can deploy agents to coding tasks
- You cannot approve architectural changes (that's Chief Architect)
- You ARE accountable for code quality and test coverage
- You ARE accountable for flagging blockers to Chief Architect

## This Week's Handoff
- Previous Lead Dev completed #539 (test button fix)
- Two issues remain in progress (#540, #541)
- Cursor agent is stuck on async socket handling
- Recommendation: Start with Claude Code for #540, then pair with Cursor for #541

[Full BRIEFING-ESSENTIAL-LEAD-DEV.md follows]
```

**Duration**: 5-10 minutes to read
**Frequency**: First time in role, when role changes, when role briefing updates
**Mandatory**: Yes, for role transitions
**Optional**: No—if you're new to a role, Piper refuses to proceed until you've confirmed understanding via questionnaire

#### 3. **Project Context Brief** (If project/milestone changed)

**What it covers:**
- Current milestone and position
- What's in this milestone (scope, goals, acceptance criteria)
- What's open right now (blockers, decisions, unknowns)
- Related milestones (what comes next, what depends on this)
- Key patterns/protocols in use

**Generated by**: PPM or Chief Architect
**Delivered as**: Linked document + summary in chat
**Example**:
```
# BRIEFING: M1 Context

You are working on M1: Foundation (MVP Foundation Epic)

## Current Status
Position: 4.4 (47% complete as of Mar 4)

## Scope
- Security: OAuth flow completion (#472)
- Testing: Error path UX (#557), fresh-account testing gate
- Architecture: MUX-OBJECTS-VIEWS completion (#706)
- Polish: Bounded UI refinement

## Open Questions
- OAuth scope for Slack integration: draft or production?
- WebSocket error strategy: retry, graceful degrade, or hard fail?
- Test gate timing: M1 gate or M2?

## Depends On
- M0 shipped (✅ Complete)
- GLUE epic resolved (✅ Complete)

[Full briefing follows]
```

**Duration**: 3-5 minutes to understand
**Frequency**: When milestone changes, when milestone context updates
**Mandatory**: Yes, for milestone transitions
**Decision**: Should Piper enforce questionnaire after project context brief? (Needs PPM input)

#### 4. **Methodology & Patterns Brief** (If new to Piper or patterns changed)

**What it covers:**
- Core methodology (Inchworm Protocol, Excellence Flywheel, etc.)
- Key patterns you'll use (Verification-First, Green Tests Red User, Assembly Assumption)
- Naming conventions and file structure
- Session log expectations and format
- How to raise blockers and questions

**Generated by**: CIO or Chief Architect
**Delivered as**: Handbook reference (in Piper's knowledge) + key protocols extracted
**Example**:
```
# BRIEFING: Methodology & Patterns

## Inchworm Protocol
Each phase is 100% complete before advancing. No exceptions.

When you say something is done:
1. Tests pass (not skip, not fail)
2. Evidence visible (transcript, terminal output, test results)
3. Documentation updated
4. Handoff notes written

Anything less = not done.

## Key Patterns You'll Use
- Pattern-045 (Green Tests, Red User): Passing tests don't guarantee working UX
- Pattern-062 (Assembly Assumption): Post-sprint integration requires Wiring Pass
- Verification-First: Verify before assuming; don't claim done without proof

[Full patterns follow]
```

**Duration**: 10-15 minutes to absorb
**Frequency**: First time, when methodology changes, quarterly refresh
**Mandatory**: Yes
**Enforcement**: Piper should ask agent to summarize Inchworm Protocol before letting them mark something "done"

#### 5. **Capability & Constraint Inventory** (Always, on entry)

**What it covers:**
- What tools/integrations Piper has access to (Slack, GitHub, Notion, etc.)
- What Piper CAN do well (conversation, coordination, pattern matching)
- What Piper CANNOT do (run code, read files outside knowledge, access external APIs directly)
- What changed since last session (new integrations, deprecated tools)
- How to request new capabilities

**Generated by**: CIO or Chief Architect
**Delivered as**: Quick reference (not a full document)
**Example**:
```
# Piper's Capabilities This Session

✅ Can Do:
- Coordinate agent workstreams
- Generate briefs and session logs
- Query GitHub issues and PRs
- Understand domain patterns
- Run Agent UX testing

❌ Cannot Do:
- Execute code (that's agents' job)
- Access your local filesystem
- Integrate with tools not configured
- Make autonomous decisions on roadmap

⚠️ Changed Since Mar 9:
- Slack integration now has OAuth (was token-based)
- New Serena symbolic queries available
- Notion API updated (no functional change to Piper's use)

Need something new? Ask in #piper-dev
```

**Duration**: 2-3 minutes
**Frequency**: Every session start
**Mandatory**: Yes
**Why**: Prevents false confidence (the Klatch failure mode)

## The First-Run Flow

### When a New Agent Session with Piper Starts

1. **Piper detects it's a new session** (or resumption of prior session)
   - If resumption: Fetch prior session's metadata
   - If new: Gather context (who is agent, what role, what project?)

2. **Deliver Session Orientation Brief** (30 seconds)
   - What's changed since last session (if returning)
   - Current project position
   - Today's agenda (if known)

3. **Deliver Capability/Constraint Inventory** (2-3 minutes)
   - What Piper can and can't do
   - What changed
   - How to request new capabilities

4. **Detect Role & Deliver Role Briefing** (5-10 minutes)
   - If new to role: Full role briefing
   - If returning to role: "Same role as last session. Any questions?"
   - Piper offers questionnaire (optional)

5. **Detect Project/Milestone & Deliver Context Brief** (3-5 minutes)
   - Current milestone and status
   - What's open today
   - Key decisions to be aware of
   - Piper offers questionnaire (optional)

6. **Deliver Methodology/Patterns Brief** (10-15 minutes, but only first time or when changed)
   - Inchworm Protocol
   - Key patterns
   - Session logging expectations
   - Enforcement points

7. **Confirm Understanding** (via questionnaire, not optional for transitions)
   - Ask 3-5 targeted questions about role, context, methodology
   - If agent answers poorly, cycle back to relevant brief
   - Only proceed to work once agent demonstrates understanding

8. **Ready to Work**
   - Agent has full context
   - Agent knows what changed
   - Agent knows constraints
   - Agent has asked clarifying questions
   - Session is logged with full briefing context

## Design Decisions Needing Stakeholder Input

### For CIO (Methodology)
1. **Should methodology brief be mandatory for every session?** (Proposal: no, only when methodology changes)
2. **Should Piper enforce questionnaire after briefing?** (Proposal: yes, for role/context transitions; optional for routine sessions)
3. **What's the definition of "understanding confirmed"?** (Proposal: agent can summarize Inchworm Protocol and current blockers)

### For HOSR (Testing & Deployment)
1. **Who generates session orientation brief?** (Proposal: Chief of Staff agent)
2. **Who generates role briefing?** (Proposal: role's prior holder + HOSR oversight)
3. **How do we validate brief quality?** (Proposal: use Agent UX testing before wider deployment)
4. **What's the fallback if agent doesn't confirm understanding?** (Proposal: Piper pauses and asks for help)

### For PPM (Roadmap & Timing)
1. **When should we launch this briefing system?** (Proposal: M1, as part of Piper's first self-deployment)
2. **Should we test it with human PMs first, or agents?** (Proposal: test with agents first via Recommendation #1, then expand to humans)
3. **Should brief generation be automated (Piper creates it) or human-curated?** (Proposal: hybrid—Piper generates drafts, humans review/approve)

## What This Requires

### Development
- **Brief template system** — Generate briefs from structured data (role, milestone, patterns, constraints)
- **Session state tracking** — Know what's new since last session, what changed
- **Questionnaire engine** — Integrated with session logging, can detect understanding gaps
- **Context transition detection** — Recognize when role changed, milestone changed, tool changed

### Content
- **Structured briefing data** — Role briefing specs, project context specs, capability inventories
- **Pattern catalog in JSON** — Machine-readable version of key patterns for Piper to reference
- **Fallback briefs** — Static versions in case dynamic generation fails

### Process
- **Brief review workflow** — Who approves briefs before they're delivered to agents?
- **Brief versioning** — How do we track changes to briefs over time?
- **Questionnaire templates** — What questions does Piper ask for each type of brief?

---

## Expected Outcomes

### If This Works Well
- Agents always know their context and constraints
- False confidence goes down significantly
- Handoffs between agents are cleaner
- Session logs include full briefing context
- We can use Agent UX testing to iteratively improve briefs

### If This Doesn't Work Well
- Briefs are too long (agents skip them)
- Briefs are too generic (don't fit specific agents)
- Questionnaires are too strict (slow down productive work)
- Automated generation produces errors (needs human oversight)

**Mitigation**: Use Recommendation #1 (Agent UX testing) to detect these failures early, iterate.

## Prototype Scope (M1 or M2)

### Minimum Viable Briefing
For first prototype, focus on:
1. ✅ Session orientation brief (already have structure)
2. ✅ Capability/constraint inventory (essential for safety)
3. ✅ Role briefing (critical for context)
4. ❌ Project context brief (can defer to full document reference initially)
5. ❌ Methodology brief (reference BRIEFING-METHODOLOGY.md instead)

### First Test Case
- **Agent**: Lead Developer (first role to get this)
- **Test scenario**: New Lead Dev session starting an implementation task
- **What we measure**: Does briefing prepare agent? Does questionnaire reveal gaps? How long does onboarding take?

### Success Criteria (M1 or M2)
- Agent completes onboarding in < 5 minutes (excluding reading time)
- Agent answers questionnaire with 90%+ accuracy
- Agent reports "feels fully oriented" in retrospective
- No "I didn't know I couldn't do X" moments during work

---

## Integration Points

### With Agent UX Testing (Recommendation #1)
- First-run briefing is the ideal testing target
- Use structured questionnaire to validate brief quality
- Each briefing iteration should be tested before wider deployment

### With Session Logging
- Session logs should include: briefing version, questionnaire responses, what agent already knew
- Track briefing efficacy over time
- Feed results back into briefing design

### With Role Management (HOSR)
- When agent transitions roles, trigger full re-briefing
- When role briefing updates, notify agents in that role
- Track when agents were last briefed on current role/context

### With Roadmap (PPM)
- As milestones change, update project context briefs
- As priorities shift, update session orientation briefs
- Schedule brief reviews in sprint planning
